# 社保缴费对账（深圳）

对账范围：单位月度缴费汇总、员工逐月逐险种明细、到账状态、申报辅助。目标是在不依赖任何非官方接口的前提下，把「社保局应缴—税务申报—银行实缴」三方数据落到同一张台账上，并给出差异清单。

## 接口可行性结论

结论：**不存在可用的公开接口**，方案走官方导出件导入。

| 路径 | 结论 | 依据 |
| --- | --- | --- |
| 乐企数字开放平台（自用直连） | 不适用 | 准入要求纳税信用 A/B 级、上一年度营业收入合计 5000 万元以上、前 12 个月开票量不低于 5 万份；小规模纳税人不满足 |
| 税企直连（专线/前置机） | 不适用 | 面向集团级企业，省局审批，年费与专线成本远高于收益 |
| 省局「地方特色集成」 | 不适用 | 面向银行、代账软件、政务平台的页面级集成，不对外开放 |
| 客户端/RPA 自动化 | 禁止 | 绕开技术措施获取数据，违反用户协议与《网络安全法》第 27 条，且双因子与风控会导致频繁封号 |
| **官方导出件导入** | **采用** | 数据由企业自有账号导出，来源合法，格式稳定 |

数据归属决定了「都要」必须双源采集：**逐员工逐月明细以电子税务局导出为准**，**参保人数与险种以社保局参保证明为准**，**到账以税库银/银行回单为准**。

## 数据来源（深圳）

| 来源 | 路径 | 产出 | 用途 |
| --- | --- | --- | --- |
| 全国统一规范电子税务局（企业登录） | 地方特色 → 社保业务 → 查询统计 → 单位申报明细查询 → 导出职工明细 | Excel | 逐人逐月申报明细（主数据） |
| 社保费管理客户端 | 查询统计 → 社保费申报明细查询 → 同步 → 导出 | Excel | 申报明细备用来源与到账状态 |
| 全国统一规范电子税务局 | 地方特色 → 社保业务 → 证明打印 → 单位缴费证明 / 单位完税证明 | PDF（带验真码） | 实缴凭证与对外证明 |
| 深圳市社会保险基金管理局 | 单位参保证明查询打印 | PDF | 参保人数、险种口径核对 |
| 开户行网银 / 税库银 | 扣款回单 | PDF/Excel | 实缴流水 |

导入件必须原样归档，解析结果与原始件通过 `si_import_batch.file_hash` 关联，重复导入幂等。

## 数据模型

新增表统一前缀 `si_`，迁移从 `V33` 起，字段规范与 [V10](../backend/src/main/resources/db/migration/V10__add_employment_periods.sql) 一致（`created_at`/`updated_at`/`updated_by`）。

| 表 | 职责 | 关键列 |
| --- | --- | --- |
| `si_import_batch` | 导入批次与幂等 | `source`、`period CHAR(6)`、`file_hash`、`row_count`、`imported_by` |
| `si_declaration` | 单位月度申报汇总 | `period`、`insurer`、`headcount`、`base_total`、`amount_unit`、`amount_personal`、`amount_total`、`status` |
| `si_declaration_item` | 员工逐月逐险种明细 | `declaration_id`、`employee_id`、`insurer`、`base`、`amount_unit`、`amount_personal` |
| `si_payment` | 实缴流水 | `period`、`paid_on`、`amount`、`voucher_no`、`receipt_key` |
| `si_participation` | 参保状态 | `employee_id`、`insurer`、`started_on`、`ended_on` |
| `si_reconcile_diff` | 差异清单 | `run_id`、`type`、`employee_id`、`period`、`expected`、`actual`、`status`、`note` |

员工关联优先走身份证盲索引（[`PiiCipher`](../backend/src/main/java/com/jianheng/emp/security/pii/PiiCipher.java) 的 `id_card_bidx`）；导出件证件号脱敏时降级为「姓名 + 任职区间」匹配，仍无法唯一确定则进入人工指派，不做模糊猜测。在职口径以 [`employment`](../backend/src/main/resources/db/migration/V10__add_employment_periods.sql) 未离职记录为准。

## 对账规则

三层校验，逐层输出差异：

| 层 | 校验 | 差异类型 |
| --- | --- | --- |
| L1 汇总 | 明细汇总 = 申报汇总 = 实缴金额 | `AMOUNT_MISMATCH`、`UNPAID` |
| L2 人员 | 在职名单 = 参保名单 | `MISSING_PARTICIPATION`（漏参）、`EXTRA_PARTICIPATION`（离职未减员） |
| L3 基数 | 申报基数 = 应缴基数口径，且在上下限内 | `BASE_MISMATCH` |

另有 `REFUND`（退费冲抵）、`DUPLICATE`（重复申报）两类按流水识别，不参与三层汇总。

差异状态机：**待处理 → 已确认（差异合理）/ 已修复（下月调平）/ 已忽略（必填原因）**，每次流转写 [`audit_event`](../backend/src/main/java/com/jianheng/emp/web/AuditMapper.java)，操作类型前缀 `SI_`。

基数上下限、险种与档次、申报期限全部按年度配置，**不写死在代码里**——深圳社保年度为 7 月至次年 6 月，每年调整一次。

## 申报辅助

无接口意味着申报仍要人工在电子税务局操作，系统提供的是「对照单」：

- 月度增减员清单：在职名单与上月参保名单差集，直接对应电子税务局的增员/减员操作。
- 申报底稿：期间、人数、基数合计、应缴金额、上期实缴、差异项。
- 台账导出：复用现有 [Apache POI 导出](../docs/mvp-design.md) 能力，字段与财务台账一致。

## 合规边界

- 数据来源限定为企业自有账号导出，不引入第三方代查。
- 社保缴费记录属敏感个人信息，访问权限限财务、人事与管理员，且纳入现有 PII 加密与审计。
- 原始导出件按附件保存（[`AttachmentService`](../backend/src/main/java/com/jianheng/emp/approval/AttachmentService.java)），与数据库备份同窗口。

## 验收场景

1. 导入某月电子税务局职工明细与银行回单，L1 三层金额一致时无差异；不一致时差异可定位到人或到账。
2. 员工离职当月未减员，次月对账产出 `EXTRA_PARTICIPATION`，确认后进入下月减员清单。
3. 同一份导出件重复导入不产生重复数据（`file_hash` 幂等）。
4. 身份证脱敏的导出件能通过姓名 + 任职区间匹配，无法匹配时进入人工指派而非误配。
5. 退费冲抵月份，L1 不误报金额不平。
6. 差异状态流转可在操作审计中追溯。

## 待确认

- 是否存在多主体（多个单位编号）需要合并对账。
- 导出件中身份证是否完整，决定自动匹配率。
- 差异确认后是「下月调平」还是「当月补缴」，影响申报辅助的输出形态。
- 是否需要把对账结果同步到员工档案（参保状态展示）。

## 不做的范围

自动申报、自动扣款、发票与完税证明验真、跨省多主体合并、薪酬核算联动。
